### 7.11 BestEffortFieldAssessmentRecord

Every active field applicable to every present owner instance in the final

the ambiguity between “not evaluated,” “evaluated but no value supported” and
“value produced.”

|---|---|---|
| assessmentIdentity | exactly 1 | The bestEffortAssessmentIdentity defined in §7.1. |
| fieldIdentity | exactly 1 | One active c4.besteffort.field.* identity. |
| capabilityIdentity | exactly 1 | Must equal the field's registered capability parent. |
| ownerIdentity | exactly 1 | Resolvable subject instance. |
| ownerKindIdentity | exactly 1 | Must equal the field registration. |
| roomCaseIdentity | exactly 1 | The operation RoomCase. |
| linkedValueIdentities | 0..N | Active immutable value revisions for this assessment. |

| contractSemanticVersion | exactly 1 | c4.semanticmodelversion.001. |

Rules:

- scalar fields link zero or one active value revision;
- multi-tag fields link zero or more unique active tag-value revisions;
- zero values require a non-empty basis set explaining why no supported value
  was emitted;
- absence is never encoded as an `unknown` field value;
- the record emits no Contract-6 determinability outcome.

### 7.12 Value cardinality, uniqueness and revision semantics

- one assessment identity per applicable field-owner pair;
- one active value revision per scalar assessment;
- one active value revision per unique tag/value element in a multi-valued
  assessment;
- duplicate active tag identities are invalid;
- every value revision identifies its predecessor when superseding;
- one value lineage exposes exactly one active revision;
- multiple AEA may support one final value revision only when they resolve to
  compatible immediate-stage provenance;
- field/value/assessment history is immutable.

### 9.6 Fingerprint and independence semantics

A contribution fingerprint uses a versioned canonical input set:

```text
RoomCase identity;
imageAsset/sourceAsset pair;
normalized locator or inference-basis identity;
evidence-kind identity;
producingStageIdentity;
producer/rule/model/configuration version;
preprocessing lineage identity;
content/integrity reference.
```

The concrete hash algorithm is implementation-owned, but its identity and
version are mandatory. Equal fingerprints are duplicate. Near-duplicate
classification requires a separately versioned deterministic equivalence rule.
Independent corroboration requires different non-equivalent contributions and
must not arise solely from repeated provider wording or duplicated imagery.

Near-duplicate classification under `c4.fingerprintrule.002` is valid only when:

1. the contributions share one original source lineage and differ only by a
   governed preprocessing derivative that adds no new visual coverage; or
2. a versioned TDH-owned duplicate/near-duplicate decision record classifies
   distinct source assets as equivalent.

Contract 4 does not invent a perceptual threshold. Any future threshold or
algorithm must be separately accepted and versioned before it can satisfy item
2.

## 17. Candidate Lock prerequisites and downstream boundary

### 17.1 Candidate Lock topology

Candidate Lock is a separate Project Owner-authorized freezing action. It is
not equivalent to Owner acceptance. Acceptable review evidence is either a
complete review of the exact lock identity or an accepted full-review lineage
plus exact limited closure verification of a bounded correction.

### 17.2 Current readiness boundary

```text
Four capability entries:
COMPLETE

Concrete field entries:
8 ACTIVE
0 RESERVED

Field/value registries:
COMPLETE FOR THE CURRENT AUTHORIZED CONTRACT-4 SCOPE

Field assessment/no-value model:
COMPLETE

Field-catalogue Candidate Lock boundary — Option A:
RESOLVED AND BINDING
```

Option A requires the first Candidate Lock to include an accepted concrete
field catalogue. This CC7 draft contains that catalogue, but the prerequisite
is not governance-complete until:

1. independent limited closure verification confirms the exact CC7 identity;
2. the Project Owner accepts that exact identity;
3. the Project Owner separately authorizes Candidate Lock issuance.

There is no blocking Owner decision inside the current authorized scope.
Future Object dimensions are an explicit upstream-authority gap, not a hidden
current Candidate-Lock prerequisite.

### 17.3 Downstream impact

Contract 4 directly feeds future Contracts 5, 6 and 10 only after their
separate authorization. This document does not open them. Later Contract-4
extensions may add accepted fields/value identities without redefining the
identity/assessment/evidence foundation established here.
